# COST-7680 Gap Analysis: Implement phase-gated reconciler skeleton

**Jira:** [COST-7680](https://redhat.atlassian.net/browse/COST-7680)
**Audited:** 2026-08-10 (updated 2026-08-14)
**Purpose:** Handoff audit of reconciler skeleton vs ticket acceptance criteria. This document does not update `docs/tasks.md` or other trackers.
**Beta scope:** ROS and Kruize are **out of beta** ([BETA-PRIORITY.md](BETA-PRIORITY.md)). Pipeline stages may still run ROS and Kruize work today; do not treat their stage readiness as a Cost beta blocker. Cost-only skip/disable → [COST-8054](../jira/COST-8054.md).

## Verdict

**All acceptance criteria are met.** The ordered phase runner drives a nine-stage pipeline with Result-based early exit, status conditions, and Kubernetes Events on key transitions. Pause/resume via annotation is implemented (PR #55). Error-path exponential backoff is handled by controller-runtime's default rate limiter; fixed-interval wait requeues are an intentional deviation (see G2). `phases_test.go` and readiness helper tests bring controller coverage to 56.3%. Individual phase *logic* is out of scope for this ticket.

## Done (meets or supersedes ticket intent)

### Ordered phase runner

Implemented in [`internal/controller/phases.go`](../../internal/controller/phases.go) and wired from [`reconcile()`](../../internal/controller/costmanagementserviceconfig_controller.go):

- `Result` (`RequeueAfter`, `Stop`) + `PhaseFn` signature
- `runPhases([]PhaseFn)` — continues only on zero Result + nil error; otherwise stops the slice
- `PhaseError` / `NewPhaseError` / `applyPhaseError` / `asPhaseError` for structured failure → status (helpers exist; see related gap on unused production path)

Entrypoint: `Reconcile` → finalizer / delete → `reconcile` → `runPhases` → `patchStatus`
([`costmanagementserviceconfig_controller.go`](../../internal/controller/costmanagementserviceconfig_controller.go) L58–95, L133–177).

`reconcileROSFeature` runs immediately before `runPhases` (policy bookkeeping, not a provisioning stage).

### Nine-stage pipeline (Jira’s five phases, expanded)

`runPhases` order in `reconcile()` (L146–156):

| # | Function | Role vs Jira |
|---|----------|--------------|
| 0 | `reconcileDiscovery` | Discovery |
| 1 | `reconcileSharedConfig` | Extra (config before workloads) |
| 2 | `reconcileInfrastructure` | Extra (bundled DB/cache readiness) |
| 3 | `reconcileValidation` | Validation |
| 4 | `reconcileMigration` | Migrations |
| 5 | `reconcileCoreServices` | Application (part) |
| 6 | `reconcileWorkers` | Application (part) |
| 7 | `reconcileEdge` | Platform (part) |
| 8 | `reconcileMonitoring` | Platform (part) |

Documented in [design-vs-jira.md](../design/design-vs-jira.md) §1 (~L67–70).

### Progression gating (Result-based)

`runPhases` does **not** call `IsStatusConditionTrue` on a prior phase. Progression is:

1. Phase returns zero `Result` + nil → next stage runs
2. Non-zero `Result` or error → later stages skip this pass
3. Conditions are written as status side effects (`DiscoveryComplete`, `DatabaseReady`, `SchemaUpToDate`, etc.)

This meets the ticket intent of ordered, gated rollout. Literal “previous condition must be True” predicates are not used — consistent with the design choice that status `Phase` is not a linear pipeline enum.

### Partial Event surface already present

Recorder: `mgr.GetEventRecorderFor("koku-service-operator")` in [`cmd/main.go`](../../cmd/main.go); RBAC `events` create/patch on the reconciler (L56).

| Reason | Type | Where |
|--------|------|-------|
| `ReconcileError` | Warning | `reconcile` / ROS feature error paths (L142, L160) |
| `Ready` | Normal | end of successful pipeline (see G3) |
| `MigrationStarted` | Normal | `runMigrationStep` on Job create |
| `MigrationComplete` | Normal | all migration steps done |
| `MigrationFailed` | Warning | Job exhausted retries |

### Requeue skeleton

Constants in the controller (L30–32):

```go
requeueFast  = 10 * time.Second
requeueSlow  = 30 * time.Second
requeueDrift = 5 * time.Minute
```

Used for wait/probe paths (`RequeueAfter` + nil error) and periodic drift correction. The reconcile error path returns `RequeueAfter: requeueSlow` **with** a non-nil `err`; controller-runtime ignores `RequeueAfter` when `err != nil` and applies its default exponential failure rate limiter instead (see G2).

## Intentional deviations (do not treat as bugs)

| JIRA | Implementation | Rationale |
|------|----------------|-----------|
| Linear status phases (`Discovering`…`Deploying`) | Status `Phase`: `Pending` / `Progressing` / `Ready` / `Degraded` + conditions | [design-vs-jira.md](../design/design-vs-jira.md) §1 — conditions are the machine API |
| Exactly 5 reconciler phases | 9 internal stages | Same doc; Progressing reason/message + Events carry stage detail |
| “Previous phase condition True” predicates | Result early-exit from each stage | Conditions remain the status contract; runner gates on Result/error |
| Individual phase bodies | Implemented under later tickets | Ticket explicitly out-of-scopes phase logic; skeleton is the runner |

## Remaining gaps (ticket-scoped)

### G1. Pause/resume via annotation — done

Annotation `costmanagementserviceconfigs.service.costmanagement.openshift.io/pause=true`
short-circuits the phase pipeline after finalizer handling. Sets `Paused=True` and
`Progressing=False` reason `Paused`; deletion still runs. Clearing the annotation
resumes and sets `Paused=False` reason `Resumed`. Covered by `pause_test.go`.

### G2. Exponential backoff requeue — done (intentional deviation documented)

Jira requires exponential backoff. Split by path:

| Path | Behavior today |
|------|----------------|
| **Error** (`return Result{RequeueAfter: requeueSlow}, err`) | controller-runtime **ignores** `RequeueAfter` when `err != nil` and rate-limits via the default `TypedItemExponentialFailureRateLimiter`. Error-path exponential backoff **already exists** (CRT default); the `requeueSlow` value on that return is ineffective. |
| **Wait / probe** (`RequeueAfter` + nil error) | Fixed `requeueFast` (10s) / `requeueSlow` (30s) — no attempt-aware growth. |
| **Drift** | Fixed `requeueDrift` (5m) after success — intentional periodic re-apply, not a backoff concern. |

**Intentional deviation:** Fixed-interval wait requeues are standard operator practice for readiness probes. Exponential backoff on wait paths would delay recovery when a dependency comes up. CRT's default rate limiter handles the error path; constant polling for readiness is the right trade-off.

### G3. Events on state transitions — done

Event surface now covers:

| Reason | Type | Where |
|--------|------|-------|
| `DiscoveryComplete` | Normal | `reconcileDiscovery` — first transition only |
| `InfrastructureReady` | Normal | `reconcileInfrastructure` — first transition only |
| `MigrationStarted` | Normal | `runMigrationStep` on Job create |
| `MigrationsComplete` | Normal | all migration steps done — first transition to `SchemaUpToDate=True` only |
| `MigrationFailed` | Warning | Job exhausted retries |
| `Paused` | Normal | `markPaused` — first transition to `Paused=True` only |
| `Ready` | Normal | end of pipeline — first transition only |
| `ReconcileError` | Warning | any phase error |

All transition Events use condition or `priorPhase` guards to avoid firing on every drift pass. The Ready Event transition bug (overwriting phase to Progressing before the guard) was fixed by capturing `priorPhase` before the reset.

Success Events are deliberately sparse ([COST-8103](../jira/COST-8103.md)):
`Ready` is the only "product is up" Event, and there are no per-component
success Events. The former `CoreServicesAvailable` Event and the mid-pipeline
`Available=True` (`KokuAvailable`) were removed — they fired when the core
Deployments became ready, before workers and Edge. Core readiness is now the
`CoreServicesReady` condition (reason `CoreServicesAvailable`); while later
stages run, `Available` is `False` `WaitingForComponents`, and it becomes
`True` only at the end of a successful pipeline.
