# COST-7686 Gap Analysis: Implement application services

**Jira:** [COST-7686](https://redhat.atlassian.net/browse/COST-7686)
**Audited:** 2026-08-13 · **Refreshed:** 2026-08-20 on PR #105 (`feat/cost-7686-readiness`)
**Purpose:** Handoff audit vs ticket acceptance criteria. Refresh also updates the COST-7686 row in [docs/tasks.md](../tasks.md) and the COST-7686 claims in [BETA-PRIORITY.md](BETA-PRIORITY.md).
**Beta scope:** Per [BETA-PRIORITY.md](BETA-PRIORITY.md) and [docs/tasks.md](../tasks.md), ROS/Kruize readiness and profile sizing are **not Cost beta blockers**. Ticket-owned Cost services (Koku API, Masu, Listener) **are**. ROS/Kruize Deployments exist only when `spec.ros.enabled=true`.

## Verdict

Koku API/Masu/Listener, optional ROS API/Processor, and optional Kruize Deployment+Service+cluster RBAC (with finalizer cleanup) exist and are wired. Django key generation matches the ticket's 50-character/charset/create-once spec. Per-component `resources` and CR `env` overrides are wired.

**G1 (ROS opt-out for workloads) is closed** on current `main`: `reconcileROSFeature` runs at the start of `reconcileCoreServices`, and `ROSEnabled(cfg)` (default `false`) gates ROS migrate, Kruize objects + cluster RBAC, ROS workers, ROS NetworkPolicies, and Envoy ROS routes. The 2026-08-13 write-up that called this dead code is stale.

Two ticket acceptance criteria that were open on 2026-08-19 are **closed in PR #105**:

1. **G2** — 5-minute wait clock → `Degraded=True` reason `DeploymentNotReady` (component name in the message) and stepped backoff. `Degraded` is cleared when the wait is under 5 minutes or the wait list succeeds; other `Degraded` reasons (`ReconcileError`, migration) are left alone.
2. **G3** — Masu, Listener, and (when ROS is on) Kruize / ROS API / ROS Processor are `isDeploymentReady`-gated, so terminal `Available=True` / `AllComponentsReady` cannot fire while those pods are down.

**G4 (profile-based sizing)** for Koku/Masu/Listener is **not implemented here**; it is owned by [COST-8095](../jira/COST-8095.md) (UI already reads `spec.profile`).

A **G1 leftover** remains in monitoring: `reconcileMonitoring` still applies `KruizeServiceMonitor` when ROS is off, which re-creates the SM that `reconcileROSFeature` just deleted. `AppServiceMonitor` still lists `ros-api` in its component `In` selector — a dead value when ROS is off, not a live scrape. That is COST-7692 / COST-8054 surface, not a Deployment AC.

## Done (meets or supersedes ticket intent)

- **Koku API** (`KokuAPIDeployment`/`KokuAPIService`), **Masu** (`MasuDeployment`/`MasuService`), **Listener** (`ListenerDeployment`) — [`internal/resources/koku.go`](../../internal/resources/koku.go). Wired with `KokuCommonEnv` (DB, cache, S3, Kafka, Django key, RBAC service, CA bundle) plus per-deployment env and `MergeEnv(spec.Env)` overrides.
- **ROS API** (`ROSAPIDeployment`/`ROSAPIService`) and **ROS Processor** (`ROSProcessorDeployment`) — [`internal/resources/ros.go`](../../internal/resources/ros.go). Applied from `reconcileWorkers` only when `ROSEnabled(cfg)`.
- **Kruize** — `KruizeDeployment`, `KruizeService`, `KruizeServiceAccount`, `KruizeConfigMap`, `KruizeClusterRole`, `KruizeClusterRoleBinding` in [`internal/resources/kruize.go`](../../internal/resources/kruize.go). Cluster-scoped ClusterRole/Binding are deleted via the CR finalizer in `reconcileDelete()` (and via `reconcileROSCleanup` when ROS is flipped off).
- **Django secret key** — `djangoSecretKey(50)` in [`internal/resources/secrets.go`](../../internal/resources/secrets.go) uses `crypto/rand` and charset `abcdefghijklmnopqrstuvwxyz0123456789!@#$%^&*(-_=+)`. `DjangoSecret(cfg)` is applied via `r.ensureSecret()` (create-only).
- **Env vars from CR spec** — `KokuCommonEnv()` ([`internal/resources/env.go`](../../internal/resources/env.go)) plus `MergeEnv`.
- **Per-component resource overrides** — `KokuAPISpec`, `MasuSpec`, `ListenerSpec`, `ROSAPISpec`, `ROSProcessorSpec`, `KruizeSpec` (and ROS poller/housekeeper) each carry `Resources corev1.ResourceRequirements`, passed into the container spec.
- **ROS opt-out (workloads)** — `reconcileROSFeature` is called from `reconcileCoreServices`. `ROSEnabled(cfg)` gates:
  - ROS migration step (`reconcileMigration`)
  - Kruize objects + cluster RBAC (`reconcileCoreServices`)
  - ROS API/Processor/Poller/Housekeeper + related CronJobs (`reconcileWorkers`)
  - Kruize/ROS NetworkPolicies (`reconcileEdge`)
  - Envoy recommendation routes (`internal/resources/envoy.go`)
  - Cleanup of leftover objects when flipped off (`ros_cleanup.go`)
  Tests: [`core_services_test.go`](../../internal/controller/core_services_test.go) (Kruize skip when ROS off), [`ros_cleanup_test.go`](../../internal/controller/ros_cleanup_test.go) (cleanup), [`workers_ingress_test.go`](../../internal/controller/workers_ingress_test.go) (ROS API / Processor wait).
- **Readiness gate (G3) + timeout (G2)** — `waitForCoreServiceReadiness` / `waitForWorkerReadiness` gate Koku API → Masu → Listener → (ROS) Kruize / ROS API / ROS Processor via `notReadyWait`. After 5 minutes: `Degraded=True` `DeploymentNotReady` with the component name and stepped backoff. `clearDeploymentNotReady` drops that condition when the wait is under 5 minutes or the wait list succeeds. Ingress and Envoy stay on their own 30s conditions (COST-7687 / COST-7688).

## Intentional deviations (do not treat as bugs)

| JIRA | Implementation | Rationale |
|------|----------------|-----------|
| Linear `Deploying`/`Ready` phase | `Phase{Pending,Progressing,Ready,Degraded}` derived from `Available`/`Progressing`/`Degraded` conditions | Documented Kubernetes-API-conventions deviation; see [design-vs-jira.md §1](../design/design-vs-jira.md#1-status-api-conditions-over-phase-enum). "Ungate the Platform phase" maps to `cfg.Status.Phase = PhaseReady` at the end of `reconcile()` once earlier stages return a zero `Result`. |
| ROS API/Processor treated as "application services" | Applied from the reconciler's internal "Workers" stage (`reconcileWorkers`), alongside Celery workers that COST-7687 owns | Cosmetic — internal pipeline staging, not a functional gap. |
| Listener has no Service | Kafka consumer Deployment only | Same shape as the Helm chart; API and Masu do have Services. |

## Remaining gaps (ticket-scoped)

None for G2/G3. Profile sizing remains [COST-8095](../jira/COST-8095.md). ServiceMonitor ROS gating remains COST-7692 / COST-8054.

### G2 / G3 — closed (was remaining on 2026-08-19)

Shared `deploymentWait` list: Koku API, Masu, Listener, Kruize (ROS on), ROS API, ROS Processor (ROS on). `Available=False` with a wait reason; after 5 minutes `Degraded=True` `DeploymentNotReady` and stepped `RequeueAfter`. A reason change (Masu up, Listener still down) or a successful wait list clears `DeploymentNotReady` so the condition cannot keep naming a component that is already ready.

Out of this ticket: Ingress / Envoy / UI 5-minute clock ([follow-up #12](../review-follow-ups.md)); RBAC API still constant `requeueSlow` (COST-7689); `isDeploymentReady` replica-count-only (former follow-up #13 — fixed by #176 and [COST-8518](https://redhat.atlassian.net/browse/COST-8518)).

### G4. Profile-based sizing — moved to [COST-8095](../jira/COST-8095.md)

`spec.profile` (`standard` / `ha`) is accepted. **UI** already applies profile defaults when `spec.ui.*.resources` are unset ([PR #65](https://github.com/project-koku/koku-service-operator/pull/65)). No Koku/Masu/Listener/ROS/Kruize builder reads `cfg.Spec.Profile`. Shared maps are [COST-8095](../jira/COST-8095.md) (P2 for beta); ROS/Kruize rows stay with COST-8054. Use per-component `spec.*.resources` until then.

The 13 Aug claim that profile is "entirely unimplemented" and tracked only in COST-7678 is stale.

## Related gaps (not in Jira body; same surface)

### G1 leftover — Kruize ServiceMonitor re-applied when ROS is off

`reconcileROSCleanup` deletes `KruizeServiceMonitor`, but later `reconcileMonitoring` always applies:

```go
resources.AppServiceMonitor(cfg),  // selector includes "ros-api"
resources.KruizeServiceMonitor(cfg),
resources.PrometheusRules(cfg),
```

with no `ROSEnabled` check (and only when `spec.monitoring.enabled` is true, the default). Effect: Cost-only installs still get a Kruize `ServiceMonitor` CR whenever Prometheus Operator CRDs exist (usually 0 targets). `ros-api` in the App SM `In` list is a dead selector value, not a scrape of a live ROS service.

This is **not** the original G1 Deployment regression. Scrape wiring is COST-7692 / COST-8054. Fix with a `ROSEnabled(cfg)` guard in `reconcileMonitoring` under those tickets. Do not block G2/G3 on it, and do not treat G1 workloads as still open.

### Tests / coverage (not ticket ACs)

- `secrets_test.go` covers storage-credentials helpers, **not** `djangoSecretKey` / `DjangoSecret`.
- No `kruize_test.go` builder coverage (ClusterRole tests exist in `kruize_rbac_test.go`).
- Other tickets' ungated Deployments (Celery, UI, ROS Poller/Housekeeper) can still be unready after this ticket's gates would pass. That is T1 in [BETA-PRIORITY.md](BETA-PRIORITY.md), owned by 7687/7690 — not a COST-7686 regression.
